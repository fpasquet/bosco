L'application du poste est une fenêtre Electron autour de l'interface de Bosco, avec une icône dans la barre système et des notifications natives. Elle est facultative : Bosco marche aussi dans le navigateur. Elle n'existe que pour Linux, en paquet `.deb` ou en AppImage, à [télécharger](/docs/download) depuis la dernière release.

Les deux embarquent tout ce qu'il faut pour tourner sans le dépôt :

- **le service** de Bosco et son interface déjà construite, avec leurs seules dépendances de production ;
- **Node 26**, pour ne dépendre ni du Node du poste ni de nvm ;
- **l'application** Electron.

Elles gardent les données de `~/.local/share/bosco`, les mêmes que le service lancé depuis le dépôt : passer de l'un à l'autre ne perd rien.

## Le paquet .deb

```bash
sudo apt install ./bosco-desktop_0.1.0-beta.1_amd64.deb
```

Il s'installe dans `/opt/Bosco`, ajoute Bosco au menu des applications et configure à l'installation le bac à sable de Chromium (`chrome-sandbox`) et le profil AppArmor qu'Ubuntu exige depuis la 23.10. C'est le choix conseillé. Si apt signale que `_apt` ne peut pas lire le fichier, copie-le d'abord dans `/tmp`.

## L'AppImage

```bash
chmod +x bosco-desktop_0.1.0-beta.1_x86_64.AppImage
./bosco-desktop_0.1.0-beta.1_x86_64.AppImage
```

Un seul fichier, sans installation, pour toute distribution Linux. Elle se met à jour seule depuis les releases : garde-la à un endroit fixe (par exemple `~/Applications`), la mise à jour la remplace sur place.

Dès son premier lancement, elle s'ajoute au menu des applications, avec son icône : `~/.local/share/applications/bosco-desktop.desktop` lance le fichier AppImage, et l'icône est copiée dans `~/.local/share/icons/hicolor/256x256/apps/`. Si tu la déplaces, l'entrée suit au lancement suivant. Pour la retirer du menu, supprime ces deux fichiers. Cette entrée porte le même nom que celle du paquet `.deb` : si les deux sont installés, le menu lance l'AppImage.

L'AppImage embarque FUSE, avec lequel elle se monte : elle ne demande au poste que `fusermount`, du paquet `fuse3` qu'Ubuntu installe d'office. Sans lui, `./bosco-desktop_*_x86_64.AppImage --appimage-extract-and-run` la lance quand même : elle se décompresse alors dans `/tmp` à chaque lancement, plus lentement.

<Callout type="warn" title="Jusqu'à la 0.1.0-beta.2 : FUSE 2 requis">
  Les AppImage jusqu'à la 0.1.0-beta.2 se montent avec FUSE 2, qu'Ubuntu n'installe plus depuis la 22.04. Sans lui,
  elles s'arrêtent aussitôt sur `dlopen(): error loading libfuse.so.2` et `AppImages require FUSE to run`. Installe-le
  (`sudo apt install libfuse2t64`, `libfuse2` sur Ubuntu 22.04 et Debian 12), ou lance-les avec
  `--appimage-extract-and-run`. Elles ne s'ajoutent pas non plus au menu des applications.
</Callout>

<Callout type="warn" title="Sans le bac à sable de Chromium">
  Une AppImage ne peut pas installer le `chrome-sandbox` privilégié ni le profil AppArmor : son lanceur ajoute
  `--no-sandbox`. Préfère le paquet `.deb` si tu veux ce bac à sable. Le [bac à sable de Bosco](/docs/guides/sandbox),
  où tournent les sessions, n'en dépend pas.
</Callout>

## Les mises à jour

Réglages › À propos dit la version qui tourne et comment Bosco est installé : paquet .deb, AppImage (mise à jour automatique) ou depuis le dépôt. Une bêta se lit « 0.3.0-beta.1 · bêta ». Bosco cherche une version plus récente une fois par jour au plus, sur le canal « Stable » ou « Bêta » (voir [Réglages](/docs/guides/settings#à-propos)).

- **AppImage** : la nouvelle version se télécharge en arrière-plan, puis le menu de la barre système commence par « Relancer pour mettre à jour · version 0.2.0 ».
- **Paquet .deb** : un bandeau « Version 0.2.0 disponible » propose le nouveau paquet. Installé pendant que Bosco tourne, il se signale : une notification « Bosco a été mis à jour » s'affiche, et le menu de la barre système commence par « Relancer Bosco · version 0.2.0 installée ».

Bosco ne se relance jamais seul : c'est toi qui choisis le moment, entre deux tours. Après une mise à jour, un bandeau « Bosco 0.2.0 installé » mène une fois aux nouveautés.

Une version plus ancienne refuse de démarrer sur des données qu'une plus récente a mises à jour. Elle affiche « Tes données viennent d'un Bosco plus récent ».

## Construire depuis le dépôt

```bash
make desktop-package           # construit apps/desktop/out/bosco-desktop_<version>_amd64.deb
make desktop-package-install   # l'installe avec apt (sudo)
make desktop-update            # git pull, pnpm install, puis construit et installe le paquet (sudo)
make desktop-release           # .deb, AppImage et fichiers de mise à jour, à la version exacte du dépôt
```

`make desktop-package` construit d'abord tout le dépôt (`make build`), puis prépare le paquet. Un seul `.deb` reste dans `apps/desktop/out` : les anciens sont supprimés. Un paquet construit hors d'une release porte la version suivie de la date et du commit, par exemple `0.1.0+git20261109073400.3118cb5` : chaque construction est plus récente pour apt. Une copie de travail modifiée prend en plus un suffixe `.dev…`.

`make desktop-package-install` copie le paquet dans un dossier temporaire lisible par l'utilisateur `_apt`, puis lance `sudo apt install --reinstall`. Sans ce détour, apt se plaint de ne pas pouvoir lire un fichier du dossier personnel.

Les releases elles-mêmes sont construites par le workflow « Release » de GitHub Actions : voir [Développement](/docs/development#publier-une-version).

## Essayer une branche : make beta

Pour essayer une branche avant sa fusion, sur tes vraies données :

```bash
make beta                          # construit la branche courante et installe son paquet (sudo)
make beta BRANCH=feat/usage-page   # une autre branche : la locale si elle existe, sinon celle d'origin
make beta BRANCH=origin/feat/x     # la version poussée sur origin, même si une branche locale existe
make beta BRANCH=main              # revenir à main
```

La branche se construit dans un worktree à part, `~/.cache/bosco/beta`, remis à neuf à chaque essai (dépendances comprises) : le dépôt courant n'est pas touché. Seul le dernier commit est construit : les modifications non commitées n'y sont pas, et `make beta` le rappelle. Une branche qui n'existe que sur origin, comme celle d'une pull request, s'essaie sans la récupérer avant ; une branche locale en retard sur celle d'origin est construite telle quelle, avec un avertissement. Le paquet remplace ensuite l'application installée.

<Callout type="warn">
  `make beta BRANCH=main` ne revient en arrière que si la branche essayée n'a pas migré la base. Sinon, la version de
  `main` refuse de démarrer sur ces données.
</Callout>

## Au lancement

L'application cherche un service Bosco sur `http://127.0.0.1:4870` :

- **aucun service ne répond** : elle démarre le sien, celui du paquet ;
- **un service répond déjà**, par exemple le service systemd de [l'installation](/docs/installation#en-faire-un-service-de-lutilisateur) : la fenêtre « Bosco tourne déjà sur ce poste » propose « Se relier au service », « Remplacer le service par l'application » (qui désactive le service systemd) ou « Quitter ». Le choix est gardé.

Si le service ne démarre pas, la fenêtre « Le service Bosco n'a pas démarré » montre ses dernières lignes d'erreur.

## La fenêtre

La fenêtre affiche l'interface de Bosco, comme le navigateur. Les liens vers l'extérieur s'ouvrent dans le navigateur. **Fermer la fenêtre la masque** : Bosco reste dans la barre système et continue de notifier. Relancer l'application ramène la fenêtre existante, sans seconde instance.

## La barre système

L'icône change dès qu'une session t'attend, et son infobulle dit combien : « Bosco · 2 sessions t'attendent ». Un clic sur l'icône ouvre la fenêtre. Le menu se lit de haut en bas :

1. « Relancer pour mettre à jour · version … » (AppImage) ou « Relancer Bosco · version … installée » (paquet `.deb`), seulement quand une nouvelle version est prête.
2. L'état : « Bosco · rien ne t'attend », « Bosco · 1 session t'attend » ou « Bosco · N sessions t'attendent ».
3. Une ligne par session qui t'attend, la plus ancienne d'abord, qui ouvre la session :
   - une autorisation : « Ajouter les catégories au budget du foyer · Bash npm run db:migrate » ;
   - une question : « Récapitulatif quotidien des réservations · question de l'agent » ;
   - un tour terminé : « Migrer le logger vers OpenTelemetry · tour terminé ».
4. « Ouvrir Bosco », « Nouvelle session » et la case « Suspendre les notifications 1 h ».
5. La case « Lancer au démarrage » et « Quitter Bosco ».

« Lancer au démarrage » écrit `~/.config/autostart/bosco.desktop` : Bosco démarre avec ta session, fenêtre fermée, dans la barre système. Pour l'AppImage, cette entrée lance le fichier AppImage lui-même.

## Les notifications

Quand l'application tourne, c'est elle qui affiche les notifications, avec celles du système : le service ne les envoie pas en double. Le titre dit le type et le projet, « Autorisation · maison », le texte donne le titre de la session et un extrait. Un clic ouvre la session dans la fenêtre.

Une autorisation ou une question part en priorité critique : elle reste affichée jusqu'à ce que tu la fermes. Rien ne s'affiche quand la fenêtre est au premier plan (l'interface montre un message bref) ni pendant une suspension d'une heure. Ce qui notifie se règle dans [Réglages › Notifications](/docs/guides/notifications).

## Lancer l'application depuis le dépôt

Pour développer l'application elle-même, sans paquet :

```bash
make desktop           # construit, puis ouvre l'application du dépôt avec le Node du poste
make desktop-install   # ajoute au menu des applications une entrée qui lance l'application du dépôt
```

Depuis le dépôt, le bac à sable de Chromium demande un `chrome-sandbox` qui appartient à root. Sans lui, l'application se lance sans bac à sable et affiche la commande `sudo chown … && sudo chmod 4755 …` qui le configure. Le paquet `.deb` le configure à l'installation ; l'AppImage s'en passe.
